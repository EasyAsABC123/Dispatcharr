# Authentication compatibility

All original application credit remains with Dispatcharr authors and contributors. See the repository attribution and AGPL license.

The pinned original runs Django 6.0.9 with PBKDF2 SHA256 at 1,200,000 iterations and 128-bit salt entropy. Native login verifies the existing Django credential in a bounded blocking pool, then upgrades a matching legacy PBKDF2 SHA1, different SHA256 work factor, or salt shorter than 22 characters. Django counts salt characters rather than UTF-8 bytes. Both username and password serializer fields trim whitespace in the pinned SimpleJWT version.

Password upgrades happen before the active-account check, matching Django ModelBackend: an inactive account with the correct old credential receives an upgraded hash and still receives 401. A failed credential never changes the stored password. A failed old SHA256 credential consumes the missing work-factor iterations in the same bounded worker. Unknown/unusable hashes consume a preferred dummy hash. Existing input, salt, iteration and worker bounds remain in force.

The native update compares the previously read password in SQL before replacement, avoiding an overwrite of a concurrent password change. The original setter saves unconditionally; this concurrency protection is an explicit implementation difference. Default Scrypt support is now component-verified separately; Argon2/bcrypt libraries are unavailable in the pinned source runtime. Unsupported/custom work factors fail closed.

`verified-auth-hash-source-1.json` binds six real original/native SQL/login cases to the captured Rust source archive and raw report digest. This host component proof does not establish packaged-image, browser, timing-equality or performance acceptance. Run `scripts/rust-integration/run_auth_compat.py --output <empty evidence directory>` with the documented disposable Docker and Rust environment. The ignored `auth_sql` test requires fixture JSON and a real migrated schema; it never silently substitutes a mock.

The original SimpleJWT configuration disables refresh rotation and does not install the token blacklist application. Its blacklist-after-rotation setting therefore does not establish token revocation. Logout flushes the Django session and records an event; existing JWTs remain valid. Native JWT revocation must not be invented as a parity fix.

Remaining authentication gates include packaged deployment and browser coverage of shared login/API-key throttles and audit/lockout effects, the other installed password hashers, Django session behavior and malformed input edge cases. XC failed-auth shared-cache authorization has its own source-bound contracts in `XC-AUTH-CONTRACTS.md`.


Shared auth histories use the original `:1:throttle_login_<IP>` and `:1:throttle_api_key_auth_<IP>` Redis keys, primitive Django pickle lists, and 60-second expiry. Login consumes allowed attempts (including serializer failures); API-key auth only consumes credential failures. Rejected attempts do not extend history expiry. Native writers compare the previously read bytes atomically and retry within a bounded budget; mixed Django/Rust concurrency cannot promise atomic legacy writers. The application wires the shared cache; constructor-only users without one retain the existing bounded local fallback.

`verified-auth-shared-source-2.json` binds six hash cases and 31 original/native throttle requests to exact captured source bytes. Two independent AuthService instances alternate requests against the same Redis. It compares all sequential audit details, notice fields, history cardinalities, response JSON and Retry-After values. This proves login validation/once-lockout and active/inactive/unknown API-key budgets; it does not prove packaged deployment or a browser workflow.

The native audit writer preserves original event retention and does not allow storage or sink errors to fail authentication. Login/API-key lockouts produce the exact cooldown-gated admin inbox and full M7 envelope. Connect integrations and plugin event dispatch remain M8 work. Reverse-proxy login audit and authenticated-user throttle bypass are implemented but need focused original role/denial probes. Non-UTF-8 key extraction, duplicate legacy API-key rows and Retry-After propagation through the media resolver remain explicit edge gaps.


The expanded `verified-auth-cache-proxy-source-4.json` records 40 shared-cache and 17 raw HTTP original/native cases. It restores original serialized histories with relative timestamps rebased to avoid fixture build-time expiration. It verifies cached UI deny policy against differing SQL, cached enabled proxy config against disabled SQL, overfull history with no Retry-After, additional serializer/audit failures, proxy availability/identity failures, authenticated anonymous-throttle bypass, refresh denial and JWT validity after logout. An earlier retained failed run identified an extra Bearer challenge on manual proxy401; the corrected wrapper omits it while retaining JWT authentication-exception challenges.

Public `AuthService::source_network_allowed(ip, key, user)` reads the shared bounded original settings cache and reuses the source global/user CIDR rules. REST and live permission helpers use it. `is_trusted_proxy(peer)` exposes exactly the peer trust used by `client_ip`, for trusted forwarded-origin builders. Reverse proxy config uses the same version-guarded grouped cache with the original disabled/header-empty defaults.

Full API comparisons now allow a real 62-second budget window before the CRUD login triple and between independent startup login pairs. They do not reset histories or bypass production throttles. IMAGE14 retains its prior captured probe tools; these waits apply to future full runs with shared auth.


IMAGE14 now also has a frozen hash-only HTTP proof: `verified-integration-m5-auth-image14-1.json` links 30 checks (18 foundation, six credential outcomes, six cleanup). It independently resets only owned credential rows before each backend, then inspects actual original-schema hashes and last_login through a guarded helper. It never resets rate histories: the two backend requests share each synthetic fixture IP's real budget. Hash bytes, plaintext passwords and JWTs are excluded from recorded outcomes; token signatures and claims are validated before normalization. Audit fields are outside this hash-only witness because IMAGE14 predates the audit port.


`verified-auth-scrypt-source-5.json` records eight original/native hash cases, including default Scrypt verification/upgrade and wrong-password preservation, with all prior 57 shared/proxy contracts rerun. Native Scrypt validates checked memory/work arithmetic before allocation inside the existing bounded password pool. Supported original default N16384/r8/p5 fits the32MiB workspace formula and8388608work cap. Higher custom configurations remain outside claimed compatibility. Complete regenerated hash spellings are compared, preventing noncanonical numeric fields from authenticating when original Django rejects them; six original low-cost spelling vectors cover this separately. No new authentication performance gain is claimed.

First-admin setup is now source-verified on the original migrated schema (`verified-first-admin-source-2.json`,25cases). This is plain Django behavior, deliberately separate from DRF serialization. Source Unicode15.1 NFKC and lowercase assignment data prevent newer Rust Unicode tables from transforming previously unassigned characters; all1,112,064Unicode scalars for each operation and context strings passed. Native schema initialization has a separate source-pinned SQL component gate; app/standalone/browser acceptance remains required.
