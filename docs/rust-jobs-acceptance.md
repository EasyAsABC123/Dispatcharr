# Durable jobs and backup acceptance sequence

Original Dispatcharr authors and contributors retain full application and algorithm credit. This acceptance sequence began as a source-based plan during a guide performance quiet window. Subsequent original-only transport/status capture and a test-only native status projection are now recorded below. Native durable dispatch, workers, scheduling and backup job endpoints remain unproved and disabled.

The existing local-file/channel/logo components and fenced lock helpers do not supply a durable task broker, scheduler or backup job API. The application must continue returning an explicit unsupported response for unimplemented dispatch instead of acknowledging a job that exists only in a process-local queue.

## Evidence captured since the initial plan

[Original Celery capture4](../scripts/rust-job-contracts/verified-original-celery-contracts-4.json) binds55 actual observations/assertions, the pinned original image/revision, exact fixture tools and [sanitized Source goldens](../scripts/rust-job-contracts/source-goldens.json). Celery5.6.3/Kombu5.6.2 really published backup/create before202, retained its queued message through producer restart, executed the original backup task on an owned copied PostgreSQL database and stored its result in a separate Redis backend. The copied database had26 nonempty tables; the default fixture database manifest was unchanged and all containers were removed. The original protocol2 JSON/base64 message shape, queuecelery, result prefix `celery-tasks:celery-task-meta-`, broker/result DB separation and observed3600-second result TTL are captured; no native interoperability is implied.

The actual invalid-ZIP restore task failed before schema replacement and returned a failure dictionary: CelerySUCCESS, HTTP200 failed. Neutral fixture tasks—not rewritten application handlers—produced STARTED/RETRY, uncaughtFAILURE, returned dictionaries and scalar/list/null results through the original worker. The Source status view's `ready().get()` propagation is captured: uncaughtFAILURE and ready non-dictionaries return500 rather than the later failed branch. A null returned error remainsJSONnull. The30 credential/token combinations preserve invalid/inactive JWT precedence, manual admin versus valid-token access, invalid-token403 and nonASCII-tokenHTML500. This AllowAny status view's manual admin fallback does not apply the list/create UI-network permission.

Original defaults were measured as track_startedFalse, acks_lateFalse, prefetch4 and broker pool10. The tracked neutral tasks explicitly override track_started; production backup tasks were unchanged. A running default task was already acknowledged while status remainedPENDING; hard-stopping its worker and starting a replacement did not immediately replay it, while fresh work succeeded. The3600-second visibility expiration itself was not observed. Fixture-only one-second result expiry proved a fresh query returnsPENDING after deletion; it does not substitute for waiting the original result TTL. Real web startup also publishes plugin refresh: its type/hash was recorded and the unrelated message quarantined in the owned broker before consumption. DVR/version startup work was suppressed through the original dispatch locks, and workers used the actual production Celery executable. Failed fixture attempts remain disclosed.

[Native status projection component1](../scripts/rust-job-contracts/verified-backup-status-component-1.json) passes11 Source entity/assertion vectors plus bounded-input and separately labeled code-derived controls in3 tests, with strict all-target Store Clippy. It is registered only under `cfg(test)`: typed snapshots are supplied directly, result bytes/nodes/depth/messages are bounded, and unobserved states remain unsupported. It supplies no Redis wire decoder, Celery exception deserializer, task authentication, physical operation ownership, executable handler, route or202 response. These narrow results do not close native durable jobs.

[Native publisher/reader interoperability1](../scripts/rust-job-contracts/verified-native-source-interop-1.json) subsequently passed65 observations with the actual original worker on a copied database. Native publication survives its CLI process exit; Source executes the captured backup task and native reads the real result from its separate backend. [Physical resource gate1](../scripts/rust-job-contracts/verified-native-job-resources-1.json) passes2 realRedis reply-proxy tests: accepted publication with withheld reply/timeouts, canceled result readers, retained caller/operation leases, capacity rejection and shutdown drain ownership. These are fixture-authorized/app-unwired component gates, with no production constructor, native task worker or202 route. Other task families/options, generic tagged-value HTTP emulation, queue/retry/idempotency recovery, scheduler and restore quiescence remain open.

The table began as static Source inspection. Capture4 now verifies the supported message/result/status and default early-ACK boundaries described above against the pinned original image. Prefetched reservation/warm shutdown, long visibility redelivery, more task families and several error boundaries remain unproved. Do not infer those from generic Celery documentation, the neutral fixture overrides or a mocked `.delay()` test.

## Implement and prove each step separately

1. **Extend original transport and status coverage.** Capture4 has completed the supported real publication/result/status/token/default early-ACK probes above. Preserve those goldens and failed attempts. Still capture prefetched reservation/warm-drain semantics, actual long visibility redelivery, additional backend outages and unobserved result states. STARTED/RETRY evidence from explicitly tracked neutral tasks must not become a claim that default backup handlers emit STARTED. Keep task arguments, JWTs and archive data private.
2. **Build a bounded native transport component.** Preserve the observed queue names, routing, serializers, result keys and expiry for supported task families. Bound message bytes, queued reservations, connection pools, active handlers, decoded result trees and diagnostics. An unsupported task must not be silently consumed. Make broker/result URL separation explicit. Keep the original application database schema unchanged unless a separately reviewed schema-compatibility gate authorizes a change.
3. **Prove durable dispatch before202.** Return success only after the owned broker accepts the task. Restart the producer and worker at each publication/claim/ack/result boundary. Observe the original behavior first, then make any stronger native crash recovery an explicit compatibility decision. Test replacement owners, delayed Redis replies, expired ownership, cancellation and drain. A caller timeout or dropped future must not release physical operation/child-process ownership early.
4. **Execute create/retention on copied databases.** Reuse the accepted PostgreSQL archive component and PG17 runtime closure. Gate actual archive effects, status/token flow, filename collisions, partial/failing archive publication and retention—not just result strings. Keep the source default database unchanged. Compare real service failures and mixed successful/failed retention deletions.
5. **Gate restore quiescence independently.** Use only explicitly authorized `rust_probe_backup_*` copied databases and owned files. Drain/fence live database users and media/job writers before destructive restore. Keep token-based status available through connection replacement, then reopen and verify actual schema/data/sequences/credentials. Test errors and interruption after each destructive phase. The original invalid-dump case can report apparent service success while leaving an empty schema; never count that as a data-preserving restore.
6. **Port scheduler writes and execution.** Compare settings, crontab/interval/PeriodicTask rows and change markers after both success and failure. Exercise enable/disable, edits, duplicate names, orphan cleanup, timezone/DST boundaries, missed ticks and concurrent scheduler owners. Restart the scheduler and verify actual queued work and resulting archives. Do not normalize away task multiplicity or partial SQL effects.
7. **Attach the native API and unchanged React flow.** Only after dispatch/status and handler restart gates pass, attach create/status/restore/schedule writes. Run real HTTP and browser polling through a backend restart and copied-database restore. Keep unsupported old-schema, SQLite, TLS and plugin cases explicit until separately tested.

## Resource and rollout evidence

Use Docker Compose with actual inspected CPU/memory limits and source/image/tool hashes. For M6 compare a fixed provider/guide input at realistic channel/programme counts while playback is active; for M8 compare archive size, elapsed work, whole-service CPU and sampled working memory with identical copied data. Include PostgreSQL, Redis and declared child processes. Record allocation/queue/connection peaks, OOM/counter resets, cleanup and slow/canceled consumers. Freeze workloads and thresholds before native results; retain failed attempts rather than replacing them with a favorable run.

Final M9 acceptance still needs the complete endpoint/task inventory, unsupported-input closure, service restart and rollback rehearsal, many-channel/100+viewer workloads and the planned soak. Existing read/playback gains do not establish ingestion, backup-job or whole-application gains.
