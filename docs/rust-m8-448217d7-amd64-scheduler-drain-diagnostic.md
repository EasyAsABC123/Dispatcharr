# AMD64 restore scheduler drain diagnosis

The exact ordinary Rust `448217d7` package observed all 16 signed backup and restore calls. Its typed responses and five durable jobs matched the retained Original run. After shutdown, the archived state, archive set, independent database and control file matched their expected state. Main exited 1, with its OOM flag clear. The preflight, run, closure, evaluation and campaign exits were `0/1/0/1/1`. Exact teardown removed the owned resources and retired the exact quarantine marker.

With the existing shutdown diagnostics explicitly enabled, the scheduler reported `unsettled`. Its timer was `Done`, its slot was `Available`, its cache was `Dirty`, the checkpoint still had a `Present` cached entry, and its terminal state was `Fault` with error `Drain`. In the exact timer implementation, `finish_owned` runs the required final checkpoint sync and publishes `Drain` when dirty entries remain. SQL connection readiness and close errors have their own `Settlement` label. This narrows the failure to outstanding scheduler checkpoint state after the timer completed. The exact checkpoint identity and write ordering remain unresolved.

Both this run and the [earlier backup comparison](rust-m8-b8d39793-scheduler-drain-recovery.md) observed a successful restore replace the scheduler rows and leave the update marker absent. Sampled ticks after the replacement reported no reload. The scheduler holds a raw PostgreSQL session outside the pooled restore fence and uses the row ID for checkpoint writes. A repair must settle the old generation before replacement and reload the restored generation, including the case where a row ID has been reused.
