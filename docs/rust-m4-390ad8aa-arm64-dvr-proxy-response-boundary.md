# ARM64 DVR corruption at the proxy response boundary

A stock Original run reproduced the earlier H.264 failure. The first HTTP 200 body delivered to the recorder was exactly the first 2,558,680 bytes of the strictly decodable, hash-bound synthetic origin. All observed wire bytes were acknowledged, the tap recorded zero drops, and the response ended with a TCP FIN. That complete response stopped on an MPEG-TS packet boundary inside H.264 access unit 255. It contained the same 3,104-byte prefix of the healthy 5,170-byte source slice seen in the earlier failure. The recorder input itself failed strict decoding with exit 183. The same payload appeared as access unit 55 in the third HLS segment and access unit 255 in both the complete playlist and actual MKV. Both the playlist and MKV failed strict decoding with exit 183.

The first response's last payload preceded the persisted stop by 727.428 ms. Its FIN followed the persisted stop by 278.486 ms, and the second connection opened 117.958 µs after that FIN. The second retained body matched a contiguous 1,642,180-byte origin range beginning at byte 1,279,340, whose first normalized access unit was source slice 128. It decoded strictly. The same recorded FFmpeg process generation owned both sockets. The final MKV preserved all 256 slices from the first response and 151 from the second. This locates the malformed slice at the first proxy response boundary and its later rewind in the recorder input.

The physical Original arm exited 1 on its existing strict DVR predicate. The scoped capture observers exited 0 and independently verified exact cleanup. The same-seal Native arm did not qualify to run. M4 and its performance gate remain open. The original Dispatcharr authors and contributors and the authors of its dependencies retain full credit.
