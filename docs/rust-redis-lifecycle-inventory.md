# Redis lifecycle gates still open

Original Dispatcharr authors and contributors retain full application and algorithm credit. redis-py, redis-rs, Channels and channels-redis retain their respective implementation credit and licenses.

This is a read-only inventory after the bounded reconnect component gates149/150/152/159/161. Those gates cover six connection-owner implementations: Coordinator, TaskLocks, shared RedisTransport, ClientStore, NotificationCache and VOD SessionPool. They do not cover every service using those connections, server persistence, active media, subscriptions, jobs or full application restart. Many service instances create their own RedisTransport. Reconnecting a socket does not restore lost server state or repeat failed commands.

The observed application source is upstream revision `1241b3f7ffb2e64c8d1157ecd5e3b199af1ae430`. The Original image is pinned to `sha256:34f9011514edd31ef0ff111b5f256d2e37614fcb08a6ee1ed9eccec9251a856f`. Image34 is the separately frozen application at commit `a84d4acafe7bf70667129c5d6ddf3c74b2b505d5`. The findings below distinguish code observations from unexecuted failure hypotheses.

## Subscription details from pinned code

There are three distinct mechanisms; none should be called a generic PubSub recovery gate.

* The live Python worker uses a synchronous redis-py PubSub subscription. `apps/proxy/live_proxy/server.py` starts a dedicated listener, calls `psubscribe('live:events:*')`, retries outer failures after five seconds and closes failed PubSub/client handles. `redis/client.py`6.4.0 has an `on_connect` callback that resubscribes remembered channels/patterns. Messages sent during a disconnected PubSub interval are not made durable by that callback. The actual listener/control workflow still needs a restart test.
* `core/redis_pubsub.py` is a different helper with its own listener and reconnect logic. Its exception handler invokes `_connect()` without a surrounding second catch; a failed reconnect there can escape the listener thread. The singleton accessor creates/starts it only when absent. This is a static possible thread-liveness failure, not a measured production failure. Current live server uses its own listener instead; do not prioritize fixing an unused helper without confirming its call site.
* Browser updates use `channels_redis.core.RedisChannelLayer`, not the PubSub channel-layer backend. Source consumers join on connect and discard on disconnect. Pinned channels-redis4.3.0 uses sorted sets, receive backups and a blocking pop; default message expiry is60seconds, group expiry86,400seconds. Native RealtimeBus implements compatible sorted-set queues with bounded polling, backup acknowledgement and the same expiry constants. Native gateway's reader catches pop errors and retries; it does not recreate absent group membership.

Source Channels4.3.2 `AsyncConsumer.__call__` catches `StopConsumer`, while `await_many_dispatch` obtains task results without swallowing arbitrary receive exceptions. Thus an exhausted backend receive failure can escape Source consumer dispatch. Whether a particular outage reconnects internally, closes Daphne's socket, and triggers React's reconnect must be measured; this inventory does not assert a close code or guaranteed survival. Native ping/pong alone could leave an apparently healthy socket receiving no group events after state loss. Conversely, automatically rejoining could differ from Source if Source also remains subscribed to an empty group. The paired gate decides this.

For transient loss where data survives, an unacknowledged receive and its backup must be distinguished from a no-persistence restart where both are gone. Native Incoming retains read-byte and receive-lock ownership until its actual ACK reply. Existing delayed-reply tests prove that ownership mechanism, not delivery/duplicates/order across a real server restart. Keep exact message IDs/recipient sets and retain ambiguous sender outcomes rather than reporting every failed publish as undelivered.

## Cache and media implications

ProfileCache is independent of NotificationCache, despite both living in the Store crate. Its manual driver is stopped explicitly and on Drop. A socket conversion alone must not remove its physical reply/WriterLease retention or change Source's tolerated I/O versus surfaced server-error behavior. With persisted old cache contents, indefinitely skipped invalidation can affect another service that successfully reconnects; with empty Redis, the same error may only force SQL fallback. Both states matter.

Source `apps/output/streaming_chunk_cache.py` captures generation at stream creation; invalidation increments rather than deletes retired entries, allowing current readers/builders to finish. Source invalidation logs and catches backend failures. Therefore a lost invalidation plus persisted older cache may itself be a Source stale-cache outcome; do not invent a stronger native consistency promise. Native private fences must also keep old cleanup from deleting a replacement generation. XMLTV status/error/wait behavior and memory retention need their own actual differential.

HLS/fMP4 and live statistics use persistent names alongside process-local handles. After Redis loss, a valid local media ring is not evidence of valid shared provider/client accounting; an empty stats result is not evidence that all old media ended. The active VOD162/164 observations demonstrate this distinction. Separate body delivery, quotas, stop controls, event publication, group receipt and actual physical resource drainage.

## Evidence and scope

Read-only package inspection is stored under `artifacts/rust/redis-lifecycle-inventory-165/`. It ran the pinned image unprivileged, read-only and with `--network none`; no Redis server, Django application, database or provider was started. Installed versions observed: redis-py6.4.0, channels-redis4.3.0 and Channels4.3.2. The extracted source is ignored evidence, not vendored implementation.

The inventory adds no runtime changes.149/150/152/159/161 remain bounded component proofs, not full application, active-session, realtime, cache-generation, permissions/TLS, durability or performance acceptance. Actual image34 active HTTP166 is a valid mismatch, not an accepted active-recovery gate. Its raw evidence remains separate from this read-only source inventory.
