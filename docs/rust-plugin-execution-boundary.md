# Actual execution boundary: implementation versus evidence

No full plugin-host application has been executed by this agent. There is no actual call audit or claim that this host has passed Source/Native plugin parity. Root's initial compiler-only SDK acceptance is separate from image/runtime acceptance. Original Dispatcharr and dependency authors retain full credit.

The compatibility interpreter is not dependency-only. The full draft copies Original application library/model modules to an explicit prefix, loads actual Django apps/models, and uses original PluginManager and framework helpers so user Python plugins can perform actual ORM/Task/Event operations through native owned ports. Rust still serves the HTTP API, selects jobs, handles broker durability/revocation/results, controls the filesystem workflow and owns SQL/cache/event I/O and process retirement. It does not invoke an Original API view, management command, HTTP server, Celery worker loop or backend Task.run to complete a missing Rust operation.

The packaging follow-up narrows the copied application closure: HTTP views/routers, admin modules, management directories, WSGI/ASGI/routing entrypoints, top-level server/manage scripts, templates and tests are excluded. The native Django settings select an empty URL router and no WSGI/ASGI application. Ordinary management call_command/execute_from_command_line entrypoints are fenced before setup. Existing backend Task.run bodies are replaced before plugin discovery; their actual callable code objects are also registered with an execution guard. A forbidden original body/entrypoint retires the owned host before that body rather than raising from the profiler and allowing CPython to disable the guard. This is not a sandbox against malicious user code or C extensions.

Expected Original application code is explicitly:

- AppConfig/model import and signal registration required by Django's actual model registry. Startup uses shell/skip-initialization settings; no source web/worker startup is requested.
- PluginManager discovery, manifest/field/action normalization, task ownership, settings/context construction, run_action, stop/stop_all, schedule suspension/restoration and list_plugins. User callables themselves remain real Python. The enabled API ordering is selected in Rust while actual Django.atomic/model save/signal state lives on the same Python action thread.
- Actual model descriptors/managers/query/compiler paths, overridden model methods and attached model signals reached by user ORM or plugin framework operations. They do not define the implementation of Native HTTP routes. Original ordinary signal/helper work is not magically converted to Rust: it must be audited, and intended builtin producers must reach actual native ports or explicit refusals. The current builtin publication/eager-call ports remain guarded, so ordinary complex user model mutations may still be unsupported.
- Current-task request/context and user hook execution for the scoped event bridge, without running a builtin task body. Source Connect HTTP/script orchestration remains an independent native boundary.

`RUST_PLUGIN_EXECUTION_AUDIT=1` enables bounded actual original-file/function/call counters; no arguments, SQL, user results or credentials are logged. The host's private audit operation reports actual loaded execution origins and blocked entrypoints. A call inventory, Origin hashes, actual backend/task/model effects, worker/HTTP ownership and complete child wait/EOF must be captured in the new grouped M8 fixture before acceptance. Unexpected ordinary application helper/model-signal work is a compatibility gap to resolve, not permission to delegate the native backend back to Python.

Remaining requirements include native builtin producer/direct-call adapters, complex model-signal effects, user subprocess/background lifecycle, generic Channels receivers, actor reload/crash behavior, task-signal/monkey-patch extension semantics, transaction/timeout/caller-loss proof and the full enabled install/update/delete/history workflow. The copied files being reachable in the same image/UID is not filesystem isolation. Every actual compatibility actor and socket must be included in later resource measurements.
