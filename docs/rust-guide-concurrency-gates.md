# Remaining guide concurrency gates

Original Dispatcharr authors and contributors retain all application and algorithm credit. This is a source-based test plan, not a new passing contract or performance claim. No database, fixture or tests ran while preparing it during the isolated image28 matrix.

The current-programme component's recorded105failure showed that a repeatable-read snapshot can begin too early when a setup SELECT precedes a relation-lock wait. The corrected component uses utility setup and relation locks before its guarded snapshot;106 and107 have separate actual PostgreSQL evidence. That proof does not accept every other guide query schedule.

Grid metadata currently uses utility `SET LOCAL statement_timeout`, repeatable-read isolation, an EXISTS size preflight and the original full-width channel join. It does not use the rejected current-programme setup SELECT. Its relation-lock/snapshot behavior still needs its own measured Source comparison; do not infer a failure or a pass from a similar transaction pattern.

The original grid partitions visible channels before returning its StreamingHttpResponse. Stored programmes are queried later, when the response iterator is consumed, after its opening prefix. Native metadata and stored rows also have separate transactions, but eager native response construction and guarded snapshots can expose different refresh schedules and exception timing.

After the resource quiet window:

1. In a disposable original fixture, hold a real relation lock for a selected channel, override, EPG source or programme table. Start the original HTTP request and record which query actually waits. Observe through a separate autocommit monitoring connection; a long observer transaction must clear its PostgreSQL statistics snapshot.
2. Change only owned visibility/profile/override/EPG rows, release the lock and capture the complete original status, headers, body, statement order and side effects. Preserve the original unordered result order. Repeat with native code under the same controlled schedule.
3. Interpose programme replacement/deletion after original channel partitioning and before iteration. Capture the opening prefix and exact subsequent entity or truncation. Distinguish an original streamed200 failure from a native error before publication.
4. Exercise JSON/text growth between the bounded preflight and full projection. The client must never receive an unbounded row; document capacity errors separately from successful Source parity. Include a row that is removed before its later serialization would otherwise fail.
5. Drop the caller during each actual lock wait. Prove worker/memory credits survive until the physical query reply, rollback and connection return. Verify shutdown and final response-frame ownership separately.
6. Retain Source/native raw evidence, exact runtime/tool hashes and failed attempts. Only then change a transaction boundary or attach broader concurrency claims.

This plan does not expand the accepted43 real-clock grid cases, current-programme stable-fixture resource gains, custom dummy coverage, file dispatch or full application acceptance. A separate grid workload and frozen resource budgets are required to measure the React guide's grid endpoint itself; the stored Current/XMLTV matrix does not measure it.
