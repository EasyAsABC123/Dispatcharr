# Native Celery publication and result-decoding acceptance

Original Dispatcharr authors and contributors retain full application, protocol-integration and algorithm credit. This is a code-only plan prepared during the image25 guide performance quiet window. No native transport was implemented or executed. [Source capture4](../scripts/rust-job-contracts/verified-original-celery-contracts-4.json) supplies55 original observations; the [test-only status mapper](../scripts/rust-job-contracts/verified-backup-status-component-1.json) supplies no broker, decoder, worker or job202 authority.

The next component should publish a bounded supported task to the real original worker and read its real result before implementing a native worker. It must not consume the shared Celery queue, dispatch unsupported task families, expose backup/create or restore202, or authorize production restoration.

## Complete the original wire contract first

Capture4 records queuecelery, JSON/base64 protocol2 body shape, field names, empty create arguments, delivery mode2/priority0/routing and actual result prefix/TTL. It retains an envelope hash, not the raw envelope or every header/property value. Do not infer a complete writer schema from generic Celery documentation or from those field-name lists.

After quiet, extend the original-only disposable fixture to retain the raw message privately before a worker starts, and publish a redacted typed projection with explicit normalization rules. Capture both actual `create_backup_task.delay()` and existing invalid-ZIP `restore_backup_task.delay(filename)` messages. Preserve original tasks and Django serializers; only the copied `rust_probe_backup_*` database may be used.

Record every header/property/body field and its exact JSON type/value where deterministic. Dynamic task IDs, delivery tags, origin/reply addresses must be hashes/placeholders in published evidence, with their equality relationships verified before normalization: returned task ID versus header ID, correlation/root/parent IDs, task-token HMAC input, delivery-tag distinctness, stable or changing reply target across producer restart. Capture argsrepr/kwargsrepr, retries, eta/expires, timelimit, lang, ignore_result, group/index, shadow, stamps/stamped_headers, callbacks/chain/chord/errbacks, body encoding, content encoding/type, exchange and physical Redis list key. Observe two-message ordering and how publication is committed before the real worker consumes it. Do not assume priority buckets, routing or optional fields beyond the captured supported cases; reject unproved options in the first native component.

Record queue-binding key types/members without deleting unrelated entries. Real web startup publishes plugin refresh: retain its type/hash and quarantine it in this owned fixture before worker consumption. Use the production Celery executable and the original startup-dispatch locks to prevent unrelated plugin/provider/version/DVR work. A fixture-internal network should prevent accidental external egress. No scheduler runs.

## Bounded publisher, no native worker

The proposed narrow operation accepts a validated supported task descriptor and operator-supplied broker/result configuration, then returns a published task identity only after the actual Redis reply. Initially support only the captured create/invalid-ZIP restore probes and fixed priority/routing. The fixture must enforce broker DB8/result DB9 and an owned copied database; those numbers are fixture isolation, not a guessed production default.

Before code, pin input/serialized-envelope/result-byte ceilings, JSON nodes/depth/string lengths, queued physical commands, connection count, publication deadlines and shutdown deadlines in the component acceptance file. Reuse the existing bounded retained Redis transport where it fits. A request future's timeout/drop must retain its own physical-command permit and caller/job owner through the real Redis reply and cleanup. A caller semaphore around a detached multiplexed command is insufficient. Shutdown first closes admission, rejects new work, then waits for every physical command/owner rather than dropping observer futures.

Task IDs are generated before publication and reused through result lookup and HMAC derivation. HMAC uses the existing Django secret and Source first32 lowercase hex algorithm; no expiry/domain change may be silently introduced. Never log URLs with passwords, tokens, task arguments, raw archives or exception messages containing credentials. Task-token logic does not replace the original DRF authentication/precedence contract. There is no new public route in this component.

A timeout with a delayed publication reply is an ambiguous outcome, not permission to publish a second task. Record whether the owned task ID exists in queue/result storage and preserve the ambiguity; a retry/idempotency policy requires its own Source compatibility decision. Producer restart must not erase already accepted work. Do not use a process-local queue as proof of durability.

## Result decoder and status projection

Read only the captured `celery-tasks:celery-task-meta-` result namespace in the configured result backend, separate from broker/cache operations. Absent/expired results map through the observed Source PENDING behavior. Preserve observed status/result/date_done/children/traceback/task_id JSON shape and verify task identity before interpreting a result. Decode bounded bytes and tree shape before allocating result clones.

Complete raw result metadata is also a missing contract: capture4 saved field names/result types and hashes, not the exception-object members or every encoded value. Extend the original fixture to retain bounded private result bytes and a redacted typed projection before implementing that decoder. Kombu-tagged JSON values or exception classes outside the observed primitive result family must be explicitly unsupported until separately captured; ordinary JSON parsing is not proof that Source would expose the same typed value.

The first exception decoder supports only actual captured JSON exception shapes. Do not dynamically import arbitrary classes or assume any dict is a safe exception. Unknown status, malformed shape, unsupported exception module/type, wrong Redis type, oversized/overdeep data, invalid encoding and backend errors must be explicit unsupported/error results rather than invented completed/failed states. The existing pure mapper covers the tested typed snapshots; it does not yet establish the wire decoder.

Preserve the critical distinction: original backup tasks catch service exceptions into a dictionary, so CelerySUCCESS can mean HTTP200failed. Uncaught CeleryFAILURE propagates through `ready().get()` and yields Source500; the later failed branch is not a substitute. Ready scalar/list/null results also trigger captured attribute-error500s. Explicit null error staysJSONnull. Original result3600 TTL was measured; the fixture-only short expiry was separately labeled and cannot be reported as a3600-second wait.

## Actual interoperability and physical ownership gates

Use the pinned original Celery5.6.3/Kombu5.6.2 worker, actual Redis and copied PostgreSQL17 schema/data. Source-created envelopes/results remain the reference. Verify each operation's real queue/result effects and full HTTP status entities where applicable, with exact source/image/tool hashes and cleanup.

1. Native publication remains queued with the original worker stopped, uses the supported exact routing/body contract, survives native producer exit, and is executed exactly once by the original worker after startup. Inspect the result and real ZIP on the copied database; never restore the default database.
2. Native publication of invalid-ZIP restore is consumed by the original task, fails before schema destruction and produces the observed SUCCESS/failure-dictionary status. Copied schema/data and the default database remain unchanged at this boundary.
3. Original neutral tracked/retry/uncaught/scalar probes generate genuine backend states/results that the native bounded reader decodes and pure mapper projects exactly. Keep neutral task overrides distinct from application handler defaults.
4. Result backend separation is demonstrated with identical task ID keys/decoy keys in the other owned Redis databases; the reader must select the configured result backend. Capture actual3600 TTL and explicitly labeled short expiry/missing/WRONGTYPE/corrupt JSON cases.
5. Pause Redis responses with a controlled owned TCP proxy after the server has accepted a command. Drop/timeout the caller, verify physical command/caller permits remain held, reject excess admission, then release the reply and verify recovery. No daemon/global pause may affect other fixtures. Repeat for publish and result reads.
6. Shutdown while a physical command is delayed must reject new work and await or explicitly fail its bounded drain without releasing ownership early. Restart the producer at pre-send, accepted-command/pre-reply and post-reply boundaries; retain duplicate/ambiguous publication evidence.
7. A supported publication cannot acknowledge unrelated queue messages or modify unrelated bindings/results. Unknown task families/options are rejected before enqueue. Fixture-only plugin quarantine is not a production consumption strategy.

Defaults from Source capture4 are earlyACK, track_startedFalse, prefetch4, broker pool10 and visibility3600. These do not prove native crash recovery. Prefetched reservation/warm-drain, actual long visibility redelivery, result consistency through destructive restore, durable native execution and scheduler/beat coordination remain later gates. Any stronger native recovery than the observed early-ACK loss boundary must be documented as an explicit compatibility decision.

Only after bounded native publication/result interoperability passes should a native worker claim supported messages. Only after durable handler/restart/restore-quiescence gates pass should application APIs return202. Resource comparisons need separate frozen workload/cgroup/threshold plans; this component plan supplies no performance gain.
