# Current-programme index dispatch contract

Original Dispatcharr authors and contributors retain full application/algorithm credit and AGPL licensing. This inventory uses the pinned original `CurrentProgramsAPIView` and `find_current_program_for_tvg_id` plus the separately bound Source/current-file and index-worker evidence. It is an app-wiring gate, not proof that the current native app already starts a worker.

The HTTP endpoint is `POST /api/epg/current-programs/`. In the `epg_data_ids` branch, original code converts/truncates IDs to50, reads matching SQL programmes first and uses file fallback only for entries without a current database programme. Dummy sources are skipped. The channel branch remains SQL-only; enabling the file provider must not invent channel fallback. Normal file output is augmented with `epg_data_id`; a missing result contributes no entry.

Before publishing an index task, the original helper checks the EPG entry/source, rejects dummy and schedules-direct sources, requires a truthy TVG identifier and resolves/checks the actual file. It samples now, then reads the source index fresh. Missing index includes missing row/SQLNULL/JSONnull as characterized by the original/current lookup fixtures. Only then does it call `build_programme_index_task.delay(source.id)`. After the call returns, it returns the literal `'timeout'`; the view converts that sentinel into HTTP200 with an entry `{ "epg_data_id": <id>, "parsing": true }`. The API does not return a task ID or202 here. A scan timeout in the interleaved forward-read path instead becomes no programme; it is not an enqueue or a Parsing marker.

Publication exceptions escape before the sentinel. The original view has no catch for this dependency failure, so it produces its unhandled500 HTML response and no successful Parsing result. The native concrete dispatcher must therefore return success only after the actual broker reply; failed/ambiguous publication cannot authorize Parsing. CurrentLookup needs a distinct dispatch-failure path mapped to the Source500 response, rather than its generic503 capacity fallback. Baseline owns that targeted adapter/source HTTP gate. Deliberate resource-capacity/deadline behavior remains separately scoped, and canceled requests must not start fresh work after their deadline.

The original task's normal outcomes are SUCCESS with JSONnull, including missing source/file, successful index build and manual busy-deferral exhaustion. Busy execution publishes a new child with the same source ID, incremented `_defer_retry`, five-second ETA, retries header0 and inherited root/immediate parent. Its normal parent result contains the Source child tuple. This is not a CeleryRETRY state and not a backup-style `{status: completed}` result. The generic backup status view calls `ready().get()` then `.get('status')`; querying a normal null index result through that endpoint consequently raises Source500. Frontend retry of current programmes is the relevant workflow; a new generic completed status must not be invented.

Before the app attaches its actual file lookup/dispatcher, require an end-to-end owned copied-database witness: authenticated current request with absent index returns the exact Parsing entry only after durable enqueue; native worker completes and releases the file/SQL owners; a later current request returns the actual programme; missing/invalid/unauthorized inputs preserve source ordering; injected broker failure yields Source500 and no Parsing; canceled/paused physical replies retain owners. Production connection/library gates19+2 and immediate native index interoperability18 are prerequisites, not substitutes for this complete HTTP lifecycle. Native ETA reservation/restoration, worker startup/shutdown and exception boundaries must pass their own Source-derived gates before default worker startup.
