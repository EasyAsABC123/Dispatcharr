# Original plugin control/execution oracle

Original Dispatcharr authors and contributors retain all application and algorithm credit, branding and AGPL licensing.

[Source fixture2](verified-plugin-source-2.json) captures31 original DRF Factory responses on an owned Python plugin and nonempty copied database. [The full source data](source-plugin-control-2.json) retains role/method/status/headers/body hashes/JSON, enabled/ever-enabled/settings state and import/run/stop events. Default database manifests match before/after, owned plugin files/rows are removed, and the isolated internal Docker project is deleted. No remote repository or provider is contacted.

The original lists never-enabled plugins from declarative manifests without importing their code. Enabling imports the real Plugin class; disabling after ever-enabled remains a trusted import state. Settings preserve unknown keys and action context merges defaults without rewriting saved values. Dictionary action results pass through, scalar/list returns are wrapped, undeclared action IDs still reach the plugin's run method, and a controlled ORM action mutates its own PluginConfig row. Successful and failed actions call the actual old-connection cleanup. Reload/disable/delete invoke stop with the original reason and context. Standard users can read lists; mutations/OPTIONS use admin permissions. Factory HEAD rendering is recorded as such and does not establish a network HEAD body.

Reproduce with `source artifacts/rust/tooling/environment.sh` then `python scripts/rust-plugin-contracts/run.py --output <fresh-empty-output>`. All files, database rows, imports and ORM writes belong to the synthetic fixture. The first attempt retained a wrong backup-helper bind-mount error; fixture2 fixes the setup.

This is source behavior evidence, not a native executor, API or performance pass. Native metadata copied only from database rows would miss discovery, dynamic fields, import trust and action behavior. The existing [plugin/admin audit](../../docs/rust-plugin-admin-compatibility.md) identifies in-process Python/Django and intentional worker monkey patches; a Rust port must explicitly preserve the supported extension behavior or label its boundary. A separate compatibility execution design needs real import/reload/ORM/stop/schedule/event tests and resource/process ownership before registration. Managed ZIP/repository/signature operations, periodic-task ownership, concurrent mutation/reload, actual network/cache authentication, Django admin and full operational compatibility remain separate gates.
