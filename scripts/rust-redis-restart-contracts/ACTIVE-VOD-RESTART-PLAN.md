# Active VOD state-loss differential

Original Dispatcharr authors retain full application and algorithm credit.

The155/159 read/reseed probes do not establish active-session recovery. An actual media response, local provider handle, stream generator, body admission and profile lease can outlive lost Redis metadata. A new probe must preserve those objects across a real server restart; reseeding a replacement hash would conceal the behavior.

Use the existing disposable `scripts/rust-vod-contracts/run.py` Compose fixture, immutable Original revision/image, local `origin.py` deterministic MP4 and real Django Movie/M3UAccountProfile seeded by `seed.py`. Apply a captured overlay setting `VOD_FIXTURE_BYTES_PER_SECOND=32768` on origin. Its existing PacedWriter preserves exact file bytes/HTTP headers and prevents the entire response completing before the fault. Record full MP4 hash/size and pacing explicitly. This functional experiment has no resource-gain claim.

Source phase: a persistent controller imports the actual full `MultiWorkerVODConnectionManager` under the existing Django fixture, opens `stream_content_with_session`, and consumes exactly one8192-byte yield before a parent barrier. Keep the response, iterator, manager and cached Redis client alive. Record session/profile hash/count, current worker and local response identity. A separate fixture controller stops ONLY owned Redis with `SHUTDOWN NOSAVE` and starts the sameport/password process with persistence explicitly disabled in a new owned directory. Capture before/after run IDs and verify old keys are absent. Do not restart Django/uWSGI/provider/origin or replace the live response. Consume bounded further yields through normal EOF or a timed explicit disconnect. Capture exact bytes/hash, first failure class, metadata recreation/absence, profile counters, stop/start events and audits, then close twice and wait bounded cleanup. Retain the independently captured original MP4 to decode a completed response or report explicit truncation.

Native phase: initially use an immutable library component, with real VodEngine media pump and SessionPool/Coordinator, the same local origin/seed identifiers and request peer/headers. A persistent Rust peer holds an actual response Body across the same first-consumed-frame barrier, then the same Redis-only restart. Its request/response counters, body bytes/hash, session hash/provider counters, stop signal and shutdown outcome are measured independently. Do not substitute direct cache reads or a newly constructed pool. Match consumed byte boundaries rather than assuming native frame fragmentation equals Source8192-byte yields. After a compiled packaged app containing the accepted159 runtime exists, repeat actual authenticated HTTP requests through both backends; that is a separate app gate.

Cases should be separate fixed scenarios: active body completes after state loss; active body explicitly disconnects after state loss; immediate same-session reconnect after loss; fresh distinct session after loss; and one bounded competing same-profile session. Capture original behavior first, including whether it continues streaming without metadata and whether a later close creates/decrements missing counters. Never infer desired recovery from the healthy-start contract. Preserve Source/native mismatches and permission/quota side effects before changing runtime policy.

The supervisor must restore owned Redis on every exit, leave PostgreSQL unchanged, remove its own Compose project, and preserve raw bounded errors privately. Existing6 lifecycle cases remain unchanged and rerun as a control. No app main, Docker defaults, shared production volumes or provider jobs are involved.
