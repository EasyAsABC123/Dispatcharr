# Bounded reconnect without command replay

Original Dispatcharr authors retain application/algorithm credit. redis-rs and its ConnectionManager dependencies retain client/reconnection implementation credit.

The valid147 experiment found a real mismatch: Original redis-py recovered with the same cached object; native cached TaskLocks/RedisTransport remained failed at all three declared attempts. Fresh native objects worked on the same server.145/146 were earlier fixture setup failures, not recovery observations.

The change uses pinned redis-rs0.32.7 ConnectionManager for TaskLocks, main Coordinator and shared RedisTransport. Its inspected `send_packed_command`/pipeline implementation returns a failing command's error and atomically installs one shared connection future for subsequent operations. It does not repeat that uncertain command. Cloned managers share that future; authentication, database, protocol and supported TLS settings stay in the original Client.

Connection retries are set to zero beyond the initial attempt. Each attempt has an explicit connect bound: two seconds for TaskLocks and the existing command_timeout for Coordinator/RedisTransport. Response timeout remains unset. Existing logical deadlines and admission stay in place; a detached physical operation retains its caller and slot until an actual response/disconnection. A reconnect can finish after an errored command returns, but it cannot replay that command or mutate that command's keys. The added locked dependencies are arc-swap1.9.5, backon1.6.0 and fastrand2.5.0; redis stays0.32.7.
