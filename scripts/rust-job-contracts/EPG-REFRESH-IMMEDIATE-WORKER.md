# Fixture-only immediate native refresh execution

Original Dispatcharr authors and contributors retain full application/algorithm
credit and AGPL licensing. Celery/Kombu, Redis/redis-py, Django/PostgreSQL and
framework/dependency authors retain their credit and licenses.

The [first frozen component gate](verified-native-immediate-refresh-worker-1.json)
passes76 checks: nine supported normal scenarios, two explicit operational-gap
controls, three unsupported-head controls and three controlled real-Redis
resource tests. Its [synthetic dataset](source-native-immediate-refresh-worker-1.json)
retains actual Original producer messages, native executor/resource audits and
normal metadata decoded by Original AsyncResult. The selected changed/coupled
runtime, Cargo graph and successful tool snapshot are hash-bound in the summary.
A strict job all-target check passed before capture with selected bytes identical
to the compiled frozen fixture. Frozen workspace/regression replay is queued for
after the coordinated performance quiet window; it has not been claimed passed.

The consumer is cfg(test), guarded by copied-database fixture authority. It uses
bounded peek, exact parser and compare/pop early acknowledgement. Index-only
connections are rejected. Foreign task families, ETA messages and parented heads
remain byte-identical and unexecuted. No default loop, application startup,
public202, scheduler or production consumer constructor is added.

Supported calls use the actual FileJobRunner with a new immutable per-execution
dispatcher. Inactive/dummy/already-running, file/parser busy, missing-without-orphan,
ordinary local import, unmapped import and repeated-ID cases check their known
SQL/index/lock effects. The configured default dispatcher is never used by this
adapter. Typed index/SeriesRules children preserve root/parent context; they stay
queued and are not executed. LateProgrammes performs the existing no-new-mapping
check and refuses unproved fanout rather than inventing a Celery task family.

Typed normal result writing accepts only null or the exact missing-source string.
Source AsyncResult reads it successfully. A repeated SUCCESS ID executes the
handler again, then skips only rewriting the already stored SUCCESS bytes and
TTL. It does not skip execution. Physical release uncertainty, unknown source
support and coarse Failed do not become normal success.

The two gap controls deliberately do **not** establish Source parity. Coarse
Failed may hide a channel/runtime cause; it remains operational with no result.
A missing source with an orphan PeriodicTask also remains operational, leaving
the schedule for fixture cleanup. Source would normally return success in these
cases and clean the orphan. The fixture acknowledges the known task before
execution, so these unsupported bodies have no result. That is a deployment
blocker for general intake, not a completed rewrite behavior.

Resource tests use a controlled executor around actual Redis commands, separately
from the real FileJob scenarios. They observe early acknowledgement before a
blocked executor finishes, retain a canceled waiter through owned completion,
hold a server-written result reply through logical timeout with both admissions
retained, and require shutdown to report incomplete until the physical reply.
An idle worker drains only itself and cannot close shared transport while another
worker needs to finish. The owner closes Jobs after all workers/services drain.

The project was removed, the default database was unchanged, and an independent
container read confirmed no owned containers remained before quiet began. No
additional build/test started after the quiet cue. Next gates are frozen
regressions, native process-crash and hard-limit behavior, native ETA recovery,
exact orphan deletion/detailed failed-outcome policy and eventual application
queue/HTTP202 integration. Remote/Schedules Direct and newly mapped per-channel
jobs remain separate; full M6 and performance gains are not claimed here.
