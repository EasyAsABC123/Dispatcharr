# Bounded known-crontab scheduler

Original Dispatcharr authors retain application and algorithm credit and AGPL licensing. Celery, django-celery-beat, Kombu and timezone-data contributors retain their respective credit and notices. This extends the proven multi-entry scheduler; it does not enable scheduler intake in the application.

The native path parses bounded numeric crontab fields and calculates the pinned Celery `remaining_delta` branches using exact captured Original system timezone files. Supported zones are UTC, America/New_York, Australia/Lord_Howe, Asia/Kathmandu and Europe/Paris. Calendar inputs are limited to years 1970–2037. The implementation uses existing chrono and adds no Cargo dependency. Cached chrono-tz0.10.4 uses 2025b, whereas the pinned Original actually loads system tzdb 2026e; silently selecting the older database would change the reference. The five retained TZif files total 8672 bytes, with their hashes recorded in the calendar report. Their captured COPYRIGHT is retained with the Source evidence for the parent attribution bundle.

The database loader preserves the observed UTC-server query window: current hour ±2 plus cleanup hour 4, adjusted by the schedule timezone's fixed 2023-01-01 offset truncated toward zero in hours. Actual due calculations use each captured zone's transitions. Numeric comma/range/wrapping-range/positive-step expressions are bounded; aliases, unsupported expressions and unknown zones fail explicitly. There is no host timezone fallback or POSIX-tail extrapolation.

Reference clocks remain distinct. The original eleven vectors injected fixed-offset datetimes; their outputs are unchanged. Real `TzAwareCrontab` clocks use ZoneInfo. At the first New York fall fold, due recalculation returns 86400 seconds for the injected fixed-offset clock and 90000 seconds for ZoneInfo. The tests retain both values. Gap references also run an actual Beat process with an explicitly controlled clock dependency; this is not a claim about elapsed DST or changing the OS clock.

Crontab start times follow `CrontabSchedule.due_start_time`, rather than interval rounding. A UTC 04:00 schedule starting 04:00:01.25 aligns to the next day's 04:00. The fixture compares the raw aligned start and delay before the normal maximum-tick clamp, including a New York wildcard case where server-time conversion affects the alignment. Expired rows disable normally. Future expiry headers remain unsupported because actual worker expiration/REVOKED semantics have not been ported; the option is never discarded to manufacture a successful publication.

The exact final source map is checked across calculation vectors, SQL/tick/reload/real-timer contracts, actual native consumers read through Original `AsyncResult`, legacy single/multi interval regressions and six real resource tests. The added calendar resource case pauses actual Redis publication replies, aborts one caller and times out another, then verifies both owners/admissions remain retained, excess work rejects, short shutdown reports incomplete, actual publications settle and both counts persist before the final drain. It shares the existing bounded physical command and SQL ownership mechanisms.

The real-clock worker case publishes one inactive Refresh and one no-rules Series task. Both consumers are prepared before intake; their results are exactly null and `{"scheduled":0,"details":[]}`, counts persist as [1,1], and actual Original `AsyncResult` reads the native records. This is deliberately narrower than active import/recording-rule behavior or packaged scheduler startup.

Remaining boundaries include unknown/default task families, configured Series rules, other zones/options, future expiration, scheduler application attachment and full-M6 acceptance. Multi-dirty SQL-server-error partial commits remain a separate unresolved ordering boundary: Original drains an unordered dirty set and stops after the first SQL exception. Normal multi-dirty persistence is proved, but no lexical ordering or cross-process stable identity ordering is substituted for that error case. Calendar tests isolate this remainder instead of silently claiming it.

Retained failed attempts include Original Beat app-registry startup ordering, a premature wait before the observed spring-gap delay, a readiness callback on the initial lazy scheduler and native interval-style start rounding. Their raw reports remain in the artifact directories; successful comparisons do not overwrite or normalize them. The final public report binds exact tool/source/archive hashes, all check names and cleanup/default-database audits.
