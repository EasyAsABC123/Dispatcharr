# Known-interval native database scheduler

Original Dispatcharr authors retain application and algorithm credit and AGPL licensing. Celery and django-celery-beat authors retain framework credit and licenses. The native implementation follows the pinned Original's behavior.

The public `database_schedule` constructors now support an explicitly started, bounded **zero/one enabled known interval** lane. The application does not start a scheduler, and default intake remains disabled. Multiple enabled entries, calendar execution, unsupported tasks and unsupported options return an explicit error. Installing the six observed defaults does not grant authority to execute all six task families.

The final immutable tree passed 74 functional checks (50 actual Original reference checks, 24 native comparisons), 47 setup/resource group checks, four actual physical-resource tests, 40 default units and strict Clippy. `verified-source-native-scheduler-final-1.json` binds the exact same runtime and test map for the functional and physical proofs. Repeated reference check groups are not counted as unique cases.

The functional path uses actual Original Beat startup, elapsed one-second intervals, real workers and results as its reference. Native setup, the owned timer and existing native `RefreshApplication`/`SeriesApplication` then produce three real results per family. Both consumers are fully prepared before opening intake. Actual Original `AsyncResult` decodes those native results; graceful close persists count three. This proof covers inactive refresh and no-rules Series, with default routing/options. It does not claim active import descendants, configured recording rules or a scheduler HTTP API. The known task parsers accept only the observed bounded `periodic_task_name` extension; generic backup/index authority is unchanged.

`DatabaseSchedule::setup` preserves observed enabled/count/one-off state when installing defaults, and retains individual commit/error boundaries. Reload uses the real database change sentinel; bulk SQL changes without that sentinel intentionally leave the cache stale. The actual tick proof includes completed one-off, expiry, future start, disabled cached rows, publication denial, SQL persistence and exact known periodic frames. The timer reserves cached run state before broker publication, matching Original.

The driver starts only after explicit preparation. Stop does not abort the admitted tick. One absolute driver deadline covers its active tick, physical replies and retained final SQL sync. The physical tests demonstrate held PostgreSQL replies, caller abort, logical publication deadlines, retained admission, bounded capacity, cancellation of a shutdown waiter, a truthful incomplete short shutdown, and later full drain. Producer transports are closed by their owner after scheduler and consumer drain. The helper fixture's separate shutdown calls are not a claim that the entire assembly shares one deadline.

The loader evaluates count, field and aggregate limits server-side in one MVCC statement. Limits are 256 entries, 1 MiB aggregate string data and bounded individual fields. Oversized field, aggregate and count responses measured 1086, 304 and 249 server bytes in the final proof. This does not claim a total process RSS bound; decoder/row/context overhead remains separate. Each service permits two admitted owned operations. Existing job transport frame, queue and physical-command admission guards remain in force.

Actual Original/native hard-loss probes preserve the publication/SQL crash window: after durable publication but before first SQL sync, restart publishes another task with a distinct ID; after sync, restart preserves count one and does not republish. The controlled barrier wraps the actual publication or `_do_sync` boundary, followed by SIGKILL and a fresh scheduler process. No queued task is reinserted and no task handler is replaced. This is not an exactly-once claim.

Historical failures remain intact. The first two driver physical attempts bulk-disabled already cached defaults without the sentinel, so the expected table query was never reached. Bounded PostgreSQL diagnostics identified that fixture mistake; the corrected test sends the real marker and keeps runtime/time budgets unchanged. Four consumer-observer attempts scanned the wrong unprefixed result namespace. Original and native use `celery-tasks:celery-task-meta-*`; the observer now derives its pattern from actual `app.backend.get_key_for_task('*')`. The observer-only correction passed against the same native runtime. These failures do not establish a native execution defect. Temporary production diagnostic delegation was removed before the final replay. The unexecuted async-console experiment is excluded.

Still open: general multi-entry heap/tie order, calendar/timezone/DST and schedule options, unported default task families, configured Series recording rules, durable scheduler application configuration and packaged startup/shutdown. The public constructors and fixture application consumption do not close M6 or enable scheduler intake by default. No ledger or performance acceptance is changed by this component.
