# Stream multipart file CRUD proposal

Original Dispatcharr, Django, DRF, SQLx, axum and dependency contributors retain
all application and algorithm credit. React is unchanged. This five-path private
implementation is formatted and its Python callbacks parse; it has not been
compiled, tested or run against either application.

`overlay-map.json` binds the actual `3ca0ef4417f3187dabca98afc0b29f7ea0a1bdc8`
preimages retained under `preimages/`. `runtime-hunks.patch` is the corresponding
small-hunk join aid. Root must three-way merge these changes onto its newer SDK
source, preserving its guide/Host/public-export work. Updating preimage metadata
while copying an older full file is not a valid merge.

The actual Stream router's POST/PUT/PATCH handlers now dispatch multipart input
through the existing four Auth writer grants. A detached owned operation retains
the request/body, admission, storage work and SQL continuation if its HTTP caller
disappears. An activity registry adds no semaphore or SQL pool. Main stops intake,
joins that registry and reports unsuccessful physical drain as nonzero, including
the ordinary mode once multipart work was used. Readiness closes on an unknown
operation. JSON still reaches the original validation and shared SQL algorithm.
Known SQL failures explicitly join rollback before their operation returns.

The parser reuses axum's multipart machinery and the existing upload capacities:
5 MiB per file, 8 MiB per request, 1,000 parts and 64 KiB scalar fields. It supports
normal HTML field omission/empty/boolean handling, finite JSON `stream_stats`,
the file-vs-string validation distinction, duplicate-last file selection and
unknown-file fields that the serializer ignores. Object lookup precedes update
body parsing. Non-file validation completes before writing an upload.

Pinned Django 6.0.9 and DRF 3.18.3 bytes are bound by `source-authority.json`.
The ASCII filename domain implements basename stripping, valid-name cleanup,
the FileField 100-character check, `uploads/` prefix accounting, all suffixes
(`.tar.gz`), seven-character collision names, exclusive non-overwriting creation,
real file locking, 0644 permissions and the storage-root group behavior. A real
exclusive-create race follows Source's retry without `max_length`. The actual
parent directory descriptor anchors file creation. FileField null/empty database
preparation follows Django's FieldFile behavior while its API representation is
null. Replacing, clearing or deleting a model does not remove the earlier file;
a later SQL rejection deliberately leaves the stored orphan as Source does.

No new media-serving route is invented. The actual FileField URL is returned and
the callback observes what the normal deployment serves there. Source's media
route depends on its URL order and DEBUG/static configuration; a file URL may
reach an XC alias or the React fallback instead of returning its bytes. That
behavior is characterization until the paired observations are compared.

The callback is reachable through the existing runner copy in `cohort/`:

1. Copy `stream_file_cases.py` into the next bound readable tool closure.
2. Apply `cohort-wiring.patch` to that same copied Fixture/Workflow, preserving
   current guide/observer changes.
3. Explicitly include `stream-file-crud` for both Original and Native in that
   runner's `execution_contexts`. Its prepare runs before normal application
   startup; its run executes after the normal startup receipt. No new service,
   namespace, worker framework, image or external origin is constructed.
4. Run Source first. This is a genuinely unmeasured multipart/storage workflow,
   not a replay of the earlier ordinary JSON Stream corpus.

The workflow exercises real role denial, create, duplicate-name no-overwrite,
PATCH replacement, PUT retention, clear, finite JSON stats, empty/long-name
validation, missing-object ordering, unknown upload, multiple suffixes, a
3,000,000-byte upload, basename sanitization, storage-prefix truncation, model
delete and a real disposable PG trigger rejection after the file was written.
It captures actual HTTP bodies privately, public body hashes, SQL file names,
file bytes/modes and retained orphans. Existing context teardown owns normal
Main/role retirement. Collision suffixes and backend origins/IDs/timestamps
must be bound explicitly when comparing the two actual runs; do not erase
unrelated response or filesystem differences.

Three Rust controls are prepared for Root's joint SDK: actual filesystem
collision/suffix/length/byte/mode behavior; activity-grant retention during drain;
and actual multipart file/HTML extraction. None has been executed by this agent.

The following remain explicit unqualified domains: Unicode/entity/control and
over255 filename grammar; alternate charset or transfer-encoded multipart;
nonfinite HTML JSON; malformed boundary/error-body combinations; oversized
inputs; escaped/symlinked storage roots; storage exhaustion and permission
variants; concurrent deletion/path races; slow upload/caller-loss physical
workloads; restart and unknown SQL transport fate. An unknown SQL/panic closes
readiness and retains the original request writer, but that is not evidence of
server PID retirement or a physical pool8 bound after transport loss. Those
fault proofs remain required before full M5 or performance acceptance. This
proposal does not enable or claim backup restore, arbitrary media playback,
full filesystem compatibility or any complete milestone.
