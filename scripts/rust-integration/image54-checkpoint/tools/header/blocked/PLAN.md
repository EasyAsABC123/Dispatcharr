This controller is prepared for review; no Source or candidate application request has run. The immutable candidate is f0bfc2f200dcfd1f64ae32a9855ea250731ce67f, with the 791-file runtime map and image 53 bindings in candidate-binding.json. The accepted package and performance evidence remain image 52.

The future fixture archives the full pinned Original commit 1241b3f7 and the explicit f0 support commit from the real repository. It never archives implicit HEAD. It starts one owned Compose project and a deterministic local MP4 origin before any playback. The origin returns a controlled 404 for one separate owned Movie and emits X-Worker-ID: owned-provider-spoof on media responses. A direct Range prefix preflight binds the fixture media; it is not Source playback authority.

The copied database is migrated and seeded once with profile and account caps of 2, an actual administrator (level 10, unlimited user stream limit), a healthy Movie, a Movie with no provider relation, and a Movie whose provider returns 404. The template is cloned independently for Source and Native. The fixed nine-model/table fingerprints and all discovered sequences are checked before each phase. Source mutation cannot feed the Native clone. The default database's same named tables and sequences must be unchanged after cleanup; this is not a full-database fingerprint.

Source runs unchanged WSGI application code in one known, supervised Source-web process with direct Redis 6390 and the real 60-second read / 5-second connect settings. No view, manager, Redis method or task is replaced. Native uses the normal packaged image 53 Main and an independent Redis 6391; recovery and new default workers are not enabled. Each backend uses real SQL and Bearer authentication, including a users/me identity check.

Each phase executes these seven fixed branches, in order:

1. Valid Bearer HEAD on a routed Movie: 405, no media request.
2. Invalid Bearer GET: 401, no media request.
3. Movie with no available provider: 503, no media request.
4. Malformed UUID route: 404, no media request.
5. Healthy GET: 200, exact first 8,192 bytes and this process's worker identity.
6. Range bytes=0-8191: 206, the same prefix and cached worker identity.
7. Provider HTTP 404: application 500, with an actual new origin GET/404 receipt distinguishing this from the route 404 or unavailable-provider 503.

Native alone additionally records invalid-Bearer HEAD literally. Its static route currently predicts 405 whereas pinned Source authentication statically predicts 401. Source invalid HEAD is unmeasured and is not dispatched here. This compatibility boundary remains open regardless of the recorded Native status; it is not a parity gate.

For successful responses, the required identity is reconstructed from the actual kernel hostname and application PID/starttime. Source uses its known owned Source-web PID, never the probing Python process. Native reads /proc/1 and must have UID 65532 and command dispatcharr-rs. The HOSTNAME environment is deliberately a different canary, and the upstream origin canary must actually be observed on each healthy GET. Neither canary may become the Main worker header. Two successes must have the same actual identity. Error and HEAD branches must omit X-Worker-ID. Only controlled ASCII kernel hostnames are claimed. Syscall-failure fallback and non-ASCII/header-safety boundaries remain the separately qualified primitive component, not a live Main claim.

Each HTTP observation has an absolute 8-second clock, a joined timer and an acknowledged closed socket/inode before advancing. Headers and error bodies are bounded at 65,536 bytes. A phase lasts at most 90 seconds, including its fixed 3-second post-close settlement wait. Healthy requests deliberately close after the prefix: this does not establish complete delivery, continuous streaming, upstream sharing, or timer/counter parity. There is no counter-zero polling, cap change, reply hold, adaptive retry or input selection based on outcomes.

Cleanup attempts every owned Source-web/Redis PID/starttime stop and docker-exec collector join even after a partial capture. It then checks the default audit, stops origin and requires its handler/socket/thread terminal receipts, removes project containers/networks/volumes, and independently inventories that exact project. Process command output is collected under the existing 8 MiB in-flight bound. No usage/resource sampler runs; a cgroup identity hash is only part of the process witness.

run.py main is hard blocked before output creation or application work, with no flag or environment escape. Its implementation adapter has no CLI dispatch. A future, separately reviewed activation must supply the complete seal, exact candidate and archive, fresh Root cue, boot/time/nonce and exclusive fsynced claim before dispatch.
