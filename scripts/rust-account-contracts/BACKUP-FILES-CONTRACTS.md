# Job-free backup file API component

Original Dispatcharr authors retain full application credit and AGPL licensing. The original contracts come from `apps/backups/api_views.py`, `services.py`, `scheduler.py`, the original Django multipart parser and actual HTTP through the pinned original container. The native Store module is test-only and app/router-unwired. It does not enable backup/restore jobs, task success reports, schedule mutations or production restore authority.

The latest scoped comparison is [the native5 evidence](../rust-integration/verified-backup-api-source-native-5.json):106 ordinary original HTTP cases plus three generated large uploads,109 exact status/filesystem effects,105 fully matching captured responses and four explicitly recorded protocol differences. Its exact Rust and fixture bytes are archived. The earlier96-case/native2 report remains a historical small-upload proof.

The original four successful delete responses have status204 and no body but carry `Content-Length: 40` from a rendered JSON detail. Hyper correctly omits that forbidden header. The raw oracle remains unchanged and records all four mismatches. Secondary acceptance recognizes only four specifically named cases, requiring original204/empty-body/length40, native204/empty-body/absent-length, every other captured header and filesystem effect equal. Any other difference fails. This is not full wire parity, and there is no transport workaround.

Observed original behavior includes:

- List, upload, delete, schedule read and download-token generation require an active admin and UI network permission. Protected endpoints return401/403 before filesystem or method handling.
- Download remains `AllowAny` with normal DRF authentication first. A valid query token authorizes anonymous and nonadmin access; an invalid Bearer still fails before that token. A bad nonempty query token rejects even an authenticated admin. Empty tokens fall back to the original manual admin check, which omits UI permission; a blocked-UI admin can therefore download.
- GET-only handlers reject HEAD with405. OPTIONS list/download metadata is captured. Download bytes, size, ZIP MIME and Latin1 filename disposition are compared.
- Tokens use HMAC-SHA256 with the deployment secret and the first32 hexadecimal characters, without expiry or a separate filename/task signing domain.
- Upload accepts arbitrary file contents and extensions, including empty files. The final duplicate `file` part wins. Django filename cleanup removes path components, Windows separators and unprintable characters and applies its255-character limit. Collision suffixes precede the extension.
- Missing delete files return404; a directory returns500. Suspicious filenames return404 for reads but the original delete handler catches its own Http404 and returns500. These literal distinctions are preserved in captured cases.
- Schedule reads use the direct grouped settings row and original defaults, without scheduling a job. Broader malformed legacy schedule fields remain separately gated.

Native5's seven physical tests prove that an unread real HTTP file body retains admission, dropping it releases admission, canceling an observer retains its physically blocked filesystem worker, exhausted capacity returns503 shutdown cannot claim completion until the physical worker replies, canceled multipart bodies remove their private spool without publishing a partial upload, and schedule-only SQL reads remain available while filesystem admission is exhausted. Filesystem work has four owned permits; download chunks are64KiB. All fixture projects were removed. No performance gain is inferred from these tests.

The subsequent streaming-upload work replaces the initial8MiB whole-body cap with private disk spooling, a bounded total body, bounded fields/file count and a bounded multipart-envelope scan before Multer buffers headers. Actual original8MiB+1 and32MiB transfers, an ignored32MiB file followed by a small selected file, six exact accepted/rejected header sizes and upload cleanup passed in native5. Django includes the initial CRLF in its1024-byte header window; native3 exposed and corrected that difference. Failed attempts remain in ignored artifacts. The scanner uses fixed-size boundary matchers and no whole-file buffer, while selected files spool to private temporary disk under retained physical ownership. Ordinary tests also verify private-spool cleanup outside an active Tokio runtime.

Remaining gates include additional malformed multipart and filesystem failures, unusual filename encoding and legacy schedules, cross-replica collision behavior, packaged app routes, and the backup UI. Native download currently uses component-safe path ancestry rather than the original string-prefix test for a symlink to a similarly named sibling directory; that untested original corner is not claimed compatible. Durable202/status semantics require the shared job driver and restart recovery. Production restore additionally requires live session/pool/cache quiescence, schema upgrades and a tested restore authority. None is replaced by an in-memory success queue.

## App configuration after component promotion

The next native application source includes the job-free constructor, routes and shutdown hook; packaged acceptance still requires Root's next immutable image. `BACKUP_ROOT` uses the original environment variable and defaults to `/data/backups`. It is a filesystem path, not a URL. Relative values use the process working directory, as in the original; a deployment moving between different container working directories should supply an absolute path. Keep this directory on the intended persistent data volume.

The native image's UID65532 must be able to write the configured directory for upload/delete. Existing original volumes can have another UID; running with the matching deployment UID or an explicitly authorized ownership setup is a separate deployment step. Fixtures only initialize their own volumes and do not recursively change unrelated data.

Current bounded operating budgets are four admitted filesystem requests,128GiB total upload body,1024 bytes per multipart header window including its initial CRLF,100 file parts,1000 form parts,2.5MiB nonfile field data,100000 listed entries and64KiB download chunks. These are explicit operating limits beyond the original unbounded file-service implementation. Physical operations retain request admission after observer cancellation, and shutdown waits for their completion. Database-only schedule reads use the existing bounded Store pool and do not consume filesystem admission.

No archive is parsed or restored by these upload/download routes. Creation, restore and task-status success are not implemented by the file adapter; guarded paths return501 rather than manufacturing a202 or completed task. Scheduling writes, complete OPTIONS metadata, all malformed filesystem/parser variants, non-Latin1 download disposition, Nginx X-Accel deployment behavior and unusual legacy path cases remain separate gates. The standalone PG17 closure is still not copied into the application image, and no production restore authority is granted.
